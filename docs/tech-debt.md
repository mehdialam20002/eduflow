# Tech debt register

Every shortcut gets a row here on the day it is taken. If a row takes more than a minute to
write, it is too long. Nothing in this file is a bug: a bug goes in a GitHub issue. This file
holds work that is deliberately not done yet.

**How to use it**

- Add a row the moment you take a shortcut, in the same pull request.
- Pay it back from the weekly tech-debt budget: 20% of build time, mostly the Saturday block.
- Pay in this order: money code, then tenant safety, then anything that caused a customer-facing
  bug in the last 30 days, then the smallest jobs.
- When an entry is done, change **Fix by** to `Done <date>` instead of deleting the row. The
  history is the point.

## The entries in full

### TD-001 — the shared constants are generated by a Python script

`npm run gen:constants` runs `docs/build/gen_shared_constants.py`. That script already existed
and already reads the specification documents correctly, so rewriting it on the first day would
have bought nothing.

The cost: every machine that regenerates the constants needs Python, and the CI workflow installs
Python only for that one step. A new contributor, or a future cloud build, hits an extra
toolchain for no product reason.

The fix: port the generator to Node under `scripts/gen-constants.mjs`, keep the output identical,
and delete the `setup-python` step from `.github/workflows/ci.yml`. About three hours.

### TD-002 — CI has no coverage gate and runs no end-to-end test

The `test` job in `.github/workflows/ci.yml` runs `npm run test`, which is Vitest in each
workspace. There is no coverage threshold, and `npm run test:e2e` is not called because Playwright
is not set up yet. Both were left out because there is almost no module code to cover on Day 1,
and a gate over an empty suite teaches nothing.

The cost: a fees or payments module can reach `main` with its money paths untested and nothing in
CI objects. That is exactly the kind of gap that is discovered by a wrong receipt.

The fix: at the point where `docs/blueprint/24-testing-strategy.md` puts the coverage work
(around Day 51, prompts P-49 and P-50), switch the job to `npm run test:coverage -w server`, set
the per-area targets from that chapter, and add a Playwright job for the eight critical flows.
About half a day.

### TD-003 — the secret scan is a grep, not a scanner

`.github/workflows/security.yml` looks for a secret assigned to a string literal, for live
Razorpay, Stripe, AWS and GitHub key shapes, and for a tracked `.env` file. That catches the
mistakes that actually happen on a solo project.

The cost: it has no entropy check and no history scan, so a secret with an unusual shape, or one
that was committed and then removed, goes unnoticed.

The fix: add Gitleaks as a GitHub Action before the pilot starts, keep the grep steps as a fast
first pass, and run a one-off scan over the whole history. About two hours.

### TD-004 — `.gitignore` ignores the whole `.claude/` folder

The repository's `.gitignore` has a `.claude/` line, written when the folder held only session
state. The slash commands now in `.claude/commands/` are meant to be committed and shared.

The cost: `/new-module`, `/review-diff`, `/fix-tests`, `/security-check`, `/spec-check` and
`/daily-log` exist only on this laptop. A fresh clone, or a cloud session, has none of them.

The fix, on Day 1, is three lines in `.gitignore`:

```gitignore
.claude/*
!.claude/commands/
!.claude/settings.json
```

Keep ignoring everything else under `.claude/`, in particular any local settings file that may
hold a token.

### TD-005 — no container image and no deploy pipeline

CI checks, tests and builds, but it does not package anything. There is no `server/Dockerfile`,
no `client/Dockerfile` and no `deploy-staging.yml`.

The cost: the day the pilot needs a hosted environment, packaging and deploying get invented
under time pressure, which is exactly when mistakes with secrets and migrations happen.

The fix: follow `docs/blueprint/31-docker-and-ci-cd.md` around Day 40, well before the pilot on
Day 45. Add the server Dockerfile, the `.dockerignore`, the image build step in the `build` job,
and the staging deploy workflow. About one day.
